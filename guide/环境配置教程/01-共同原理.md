# 先把环境里的角色分清楚

一段普通C++程序通常经历：源码 → 预处理/编译 → 目标文件 → 链接 → 可执行文件 → 运行。VS Code把操作放在编辑器里，但实际工作由外部工具完成。

| 名称 | 负责什么 | 不负责什么 |
|---|---|---|
| 编辑器VS Code | 编辑、调用任务、显示调试界面 | 自己不是C++编译器 |
| C/C++扩展 | 代码提示、诊断、调试适配 | 安装扩展不等于装好GCC |
| gcc / g++ | 编译C / C++；g++自动处理常见C++运行库链接 | 不负责给STM32供电或烧录 |
| 链接器 | 把目标文件与需要的库组成程序 | 不是头文件搜索器 |
| GDB | 查看断点、变量与调用栈 | 不是编译器 |
| CMake / Ninja | 生成和执行构建规则 | 仍要有真正编译器 |
| Python辅助脚本 | 本学习区封装构建、输入、验收 | 不把C++变成Python程序 |

## 三种路径最容易混淆

| 配置 | 用在哪个阶段 | 例子 |
|---|---|---|
| PATH | 系统找可执行文件、部分运行库 | 找到g++.exe，Windows运行时找到DLL |
| -I / includePath | -I给编译器找头；includePath给编辑器提示 | 找到opencv2/core.hpp |
| -L、-l与库文件 | 链接阶段 | -lopencv_core让链接器寻找对应库 |

只给VS Code加includePath，不能自动给g++加-I；头文件不报红也可能链接失败。链接通过后缺DLL，是运行阶段的问题，继续改includePath通常无效。

## 怎样从报错定位阶段

| 现象 | 更可能的阶段 | 第一件事 |
|---|---|---|
| 找不到g++、command not found | 启动工具 | 核对可执行文件和PATH |
| fatal error: xxx.h: No such file | 编译 | 核对头文件目录、-I及环境 |
| undefined reference | 链接 | 是否遗漏.cpp或库，是否ABI/工具链匹配 |
| multiple definition | 链接 | 是否重复链接实现或多个main |
| 找不到DLL | 运行 | 检查运行时库目录与任务环境 |
| miDebuggerPath无效 | 调试器启动 | 检查GDB实际路径及所属系统 |
| 红波浪线但编译成功 | 编辑器诊断 | 看C/C++输出、compilerPath、includePath |

## 本机三套目标不能混为一谈

Windows UCRT64 g++产生Windows程序；WSL g++产生Linux ELF；arm-none-eabi-gcc产生ARM嵌入式固件。共享C/C++语言，不代表可执行文件、库、启动方式相同。WSL可以通过互操作调用Windows.exe，但那不是Linux原生构建。

一个工程先选定目标系统、架构与编译器，再配置其他部分。不要看到教程里的路径就照抄另一个环境的路径。

## 动手理解

在自己新建的练习目录里，用一个hello.cpp实验`g++ -c hello.cpp -o hello.o`，观察只生成目标文件；再用`g++ hello.o -o hello`完成链接。Windows输出可命名hello.exe。不要在原书work目录里随意覆盖已有文件。

解释两个问题：为什么装了C/C++扩展仍可能没有g++？为什么能找到头文件还可能undefined reference？能说清楚，再继续下一篇。
